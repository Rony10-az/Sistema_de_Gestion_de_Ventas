Por qué existe

Problema, solución y a quién va dirigido

Corresponde a la idea a. Sistema de gestión de ventas o inventario del enunciado, con sus cuatro módulos: productos, clientes, ventas y reportes.

Problema

  • La tienda lleva el stock en un cuaderno o en Excel, y se vende algo que ya no hay.
  • No se sabe qué productos se venden más ni cuánto se ganó en el mes.
  • El precio cambia según quién atienda.
  • Las compras a proveedores y las ventas no quedan registradas, así que no se puede saber por qué falta mercadería.

Solución

  • Productos con categoría, precio y stock, y aviso cuando llegan al stock mínimo.
  • Ventas en caja que descuentan el stock solas y emiten boleta o factura con IGV.
  • Kardex: cada entrada y salida de mercadería queda registrada.
  • Clientes con su historial de compras, y reportes con gráficos.

Dirigido a

  • Dueños de tiendas pequeñas de repuestos y accesorios de tecnología.
  • Su personal: vendedores en caja y la persona que recibe la mercadería.
  • Es un sistema interno: los clientes de la tienda no entran al sistema.

Flujo principal del negocio

De la compra al proveedor al reporte

Este es el flujo que se demuestra en vivo. Cada paso que mueve mercadería deja una fila en movimientos_inventario (el kardex).

COMPRA A PROVEEDOR→ ENTRADA DE STOCK→ VENTA EN CAJA→ COBRO→ BOLETA O FACTURA→ SALIDA DE STOCK→ REPORTES
Si no hay stock suficiente, la venta NO SE REGISTRA y se avisa qué producto falta. Si el administrador ANULA una venta, el stock vuelve a subir. Si un producto queda en su stock mínimo, aparece en ALERTAS.
Diseño técnico

Arquitectura cliente-servidor

Tres piezas separadas que se comunican por HTTP: el frontend en Next.js, la API REST en Express y la base de datos PostgreSQL. Es la misma estructura que ya tiene el repositorio de Rony.

Es un monolito modular: un solo backend, ordenado por módulos. Así lo planteó Rony en el README, y si el sistema crece, cada módulo puede separarse en su propio servicio.

Para la explicación técnica

Recorrido de una petición de Next.js a Express

Ejemplo real del flujo: el vendedor registra la venta de la boleta B001-000142.

  1. Next.jsEn /ventas/nueva el vendedor agrega los productos al carrito, elige el cliente y pulsa Cobrar.
  2. Next.jsventas.service.js llama al fetcher: POST {API}/ventas con el cliente y los productos, y el header Authorization: Bearer <token>.
  3. Expresscors comprueba que la petición venga del dominio del frontend.
  4. ExpressverificarToken decodifica el JWT y deja req.usuario = { id: 4, rol: "vendedor" }. Sin token válido responde 401.
  5. ExpressverificarRol("vendedor", "admin") deja pasar. Si fuera el almacenero, responde 403.
  6. Expressvalidar revisa que haya al menos un producto y que las cantidades sean mayores que cero.
  7. ExpressEl servicio calcula subtotal, IGV y total con los precios de la base de datos, no con los que mandó el navegador.
  8. PostgreSQLEl repositorio abre una transacción: bloquea el stock de cada producto (SELECT ... FOR UPDATE), inserta la venta y su detalle, descuenta el stock y registra la salida en el kardex. Si un producto no alcanza, deshace todo (ROLLBACK) y responde 409.
  9. Next.jsResponde 201 con la boleta; la pantalla la muestra y el dashboard ya incluye la venta.
Modelo de datos

Modelo entidad-relación

Once tablas. usuarios, productos, clientes, ventas y venta_detalle ya existen en el repositorio y se amplían; se agregan categorías, proveedores, compras, el kardex y los pagos.

Justificación

Por qué estas tecnologías

Base de datos relacional (PostgreSQL)

  • Una venta toca varias tablas a la vez: la venta, su detalle, el stock de cada producto y el kardex. Con una transacción se guarda todo o nada, y nunca queda stock descontado de una venta que falló.
  • SELECT ... FOR UPDATE evita que dos cajas vendan la última unidad al mismo tiempo.
  • Las claves foráneas impiden vender un producto o a un cliente que no existe.
  • Los reportes salen con JOIN y GROUP BY: ventas por día, productos más vendidos, ventas por vendedor.
  • Una base NoSQL (MongoDB) conviene cuando los datos no tienen estructura fija. Aquí todo tiene estructura estable y relaciones.

Next.js + Express separados

  • Next.js: páginas por rol con App Router; SSR en listados y reportes, y la caja con interacción en el navegador. Se despliega en Vercel.
  • Express: API REST ordenada por capas (rutas, controladores, servicios, repositorios). Se despliega en Render.
  • Separados, el equipo de frontend y el de backend trabajan en paralelo sin tocar el código del otro.
  • Supabase da PostgreSQL gestionado y gratuito, con conexión segura por SSL.

  • La que entra a una capa lee antes los últimos commits de su compañera en esa capa.

Cada persona de frontend consume las rutas de una persona de backend y acuerdan juntas los detalles: Rony ↔ Oscar (login y usuarios) y Jerónimo ↔ Gabriel (inventario). Al subir cambios

Reglas para no pisarse

1. Cada equipo, su carpeta

Backend solo modifica tecnifix-backend/ y frontend solo tecnifix-frontend/. Si frontend necesita algo distinto de la API, lo pide en un issue; no corrige el backend por su cuenta.

2. Dentro del equipo, cada uno sus archivos

Cada persona solo edita los archivos de su módulo (las tablas de arriba). Los archivos compartidos tienen un único dueño: Rony en backend y Oscar en frontend.

3. Todos en main, con cuidado

El grupo trabaja directo en main, sin ramas. Por eso: commits pequeños, push al terminar cada tarea y nunca más de un día con cambios sin subir.

4. Actualizarse antes de subir

Al empezar el día, antes de cada commit y antes de cada push: git pull --rebase origin main. Si aparece un conflicto, se resuelve en tu computadora; nunca se sube con conflictos.

5. Dependencias solo por el líder

Instalar paquetes cambia package.json y package-lock.json, los archivos que más conflictos causan. Se le pide al líder de la capa (Rony u Oscar) y él lo instala.

6. Migraciones nuevas, nunca editadas

Un cambio en la base es un archivo nuevo numerado, por ejemplo 003_stock_minimo.sql. Nunca se modifica una migración que ya está en main.

7. Avisar y revisar

Al subir, avisa en #tecnifix-avisos qué cambiaste. Alguien de tu capa mira el commit en GitHub y comenta si ve algo raro; si algo se rompe, lo arregla el líder de la capa con quien lo subió.

8. Los secretos no se suben

Cada uno tiene su .env local. Solo se suben los .env.example. Las claves reales van en los paneles de Render y Vercel. Lista completa más abajo.

Antes de cada commit

Esta rutina la sigue cada uno cada vez que sube algo a main.

  1. Mira qué cambió con git status. Si aparece un archivo que no es tuyo o que no tocaste, no lo subas: pregunta primero.
  2. Agrega los archivos por nombre: git add frontend/src/app/productos/page.js. Nunca git add . ni git add -A, que suben de todo, incluso lo que no debe salir de tu computadora.
  3. Revisa línea por línea con git diff --staged: sin contraseñas, tokens, console.log de datos personales, código de prueba comentado ni archivos ajenos.
  4. Corre las pruebas: npm test en backend; npm run lint y npm run build en frontend. Si algo falla, no se sube.
  5. Escribe el mensaje en español, en primera persona y con prefijo: feat: agrego el filtro por categoría en productos. Un commit por cambio lógico; no mezcles módulos.
  6. Sin firmas ni menciones de IA: borra cualquier Co-Authored-By de un asistente o texto como "generado con". El commit es tuyo.
  7. Actualízate y sube: git pull --rebase origin main y luego git push origin main. Nunca con --force. Después avisa en #tecnifix-avisos qué subiste.

Nunca se sube al repositorio

  • .env y cualquier .env.*. Solo se sube .env.example, con valores de ejemplo.
  • node_modules/, .next/, coverage/ y demás carpetas generadas.
  • .vercel/: vercel link crea ahí un archivo con un token de acceso.
  • Archivos propios de cada asistente de IA y ajustes personales del editor. Esos no van en el .gitignore: cada uno los agrega en .git/info/exclude de su copia, que es un ignore local que nunca se sube.
  • Documentos de entrega (.docx, .pdf, .pptx), capturas y notas personales.
  • Copias de la base de datos con datos reales.

Protecciones que activa Rony en GitHub

  • Branch protection en main: bloquear el force push y el borrado. Sin "Require a pull request", porque trabajan directo en main.
  • Secret scanning con push protection (Settings → Code security): GitHub bloquea el push si detecta una clave o un token.
  • GitHub Actions corre las pruebas en cada push: si sale en rojo, se arregla antes de seguir subiendo.
  • Las claves reales solo en los paneles de Render, Vercel y Supabase, nunca en el código.

Si un secreto se sube por error

Borrar el archivo en un commit nuevo no basta: queda en el historial de Git y cualquiera con acceso puede verlo. Lo primero es cambiar la clave (nueva contraseña de Supabase o nuevo JWT_SECRET) y actualizarla en Render y Vercel; después se avisa a Rony para limpiar el historial.

Avisos del equipo

Notificaciones en Discord

Igual que en la pretesis: cada vez que alguien sube commits, abre o une un Pull Request, comenta o crea un issue, llega un mensaje a Discord. Así todos saben qué se movió sin preguntar por WhatsApp.

Va en un canal propio, #tecnifix-avisos, en el mismo servidor PROGRAMANDING, separado de #fixmycity-avisos: cada repositorio tiene su propio webhook y su propio canal, así los avisos de la pretesis y los de este trabajo no se mezclan. Los 6 integrantes deben estar en el servidor; inviten a quien falte.

Opción 1 · Webhook directo (recomendada)

No necesita código: se configura una vez y ya. Es la forma más rápida.

  1. En el servidor PROGRAMANDING, crea el canal de texto #tecnifix-avisos. Si quieren ordenarlo mejor, créenlo dentro de una categoría TECNIFIX.
  2. Configuración del canal → Integraciones → Webhooks → Nuevo webhook. Ponle de nombre "TecniFix" y pulsa Copiar URL del webhook. Es un webhook nuevo: no reutilices el de #fixmycity-avisos, porque ese manda al canal de la pretesis.
  3. Pásale esa URL a Rony por privado, nunca en el grupo ni en el repositorio.
  4. Rony, en GitHub: repositorio → Settings → Webhooks → Add webhook.
  5. Payload URL: la URL de Discord con /github al final. Sin eso, Discord no entiende los mensajes de GitHub.
  6. Content type: application/json. El campo Secret se deja vacío.
  7. En eventos elige Let me select individual events y marca: Pushes, Pull requests, Pull request reviews, Issues, Issue comments y Branch or tag creation.
  8. Add webhook y prueba con un push a cualquier rama: el mensaje llega en segundos.

Opción 2 · Mensajes en español con GitHub Actions

Si prefieren avisos más cortos y en español, por ejemplo "Gabriel subió cambios a front/productos-listado", se usa el workflow de abajo.

  1. Crear el webhook en Discord como en los pasos 1 a 3 de la opción 1.
  2. Rony guarda la URL en GitHub: Settings → Secrets and variables → Actions → New repository secret, con el nombre DISCORD_WEBHOOK.
  3. Rony sube .github/workflows/discord.yml (archivo de abajo) en un Pull Request.

Usen una sola de las dos opciones; con las dos, cada aviso llega duplicado.

La URL del webhook es un secreto

Con esa URL cualquiera puede escribir en su canal de Discord. No se sube al repositorio, no se pega en el grupo y no se le pasa a la IA. Si se filtra, en Discord se elimina el webhook y se crea otro nuevo.

.github/workflows/discord.yml (opción 2)
# .github/workflows/discord.yml
# Avisa en Discord, en español, cada vez que alguien sube commits o mueve un Pull Request.
# Requiere el secreto DISCORD_WEBHOOK (Settings → Secrets and variables → Actions).
# Los datos del evento entran como variables de entorno para que un mensaje de commit
# con caracteres raros no se ejecute como código en el runner.
name: Avisos en Discord

on:
  push:
  pull_request:
    types: [opened, reopened, closed]

  avisar:
    runs-on: ubuntu-latest
    steps:
      - name: Enviar mensaje a Discord
        env:
          DISCORD_WEBHOOK: ${{ secrets.DISCORD_WEBHOOK }}
          EVENTO: ${{ github.event_name }}

Tú respondes por el código

Lee y entiende cada línea antes de subirla. En la presentación vas a explicar tu parte; si algo no lo entiendes, pide que te lo explique.

Ni paquetes ni migraciones

La IA no sube nada

La IA propone; tú haces el commit y el push. No la dejes ejecutar git add ., git push ni comandos que borren archivos.

Este archivo es la fuente única de verdad del proyecto para cualquier asistente de IA que use el equipo.

## Qué es
TecniFix es un **sistema de gestión de ventas e inventario** para una tienda de repuestos y accesorios de
celulares y computadoras (Perú, moneda soles, IGV 18 %). Módulos: productos (con categorías, proveedores,
compras y kardex), clientes, ventas (boleta o factura, pago simulado, anulación) y reportes.
No es un sistema de reservas, ni de reparaciones, ni una tienda en línea: no agregues esas funciones.

## Stack
- Backend: Node.js + Express 4, PostgreSQL con `pg` (SQL directo, sin ORM), JWT (`jsonwebtoken`), `bcryptjs`, Jest + Supertest.
- Frontend: Next.js 14 (App Router, JavaScript), React 18, Tailwind CSS y shadcn/ui.
- Base de datos: PostgreSQL en Supabase. Backend en Render. Frontend en Vercel.

## Estructura y capas
```
tecnifix-backend/    API REST. Capas: routes → controllers → services → repositories, más validators
tecnifix-frontend/   Next.js. src/app/(publico) = login; src/app/(panel) = páginas internas con menú.
                     Llamadas a la API solo por src/services + src/lib/fetcher.js
docs/                diagramas y API.md (el contrato que comparten los dos equipos)
```
- `routes`: solo define la URL, los middlewares y qué controlador atiende.
- `controllers`: lee `req`, llama al servicio y responde. Sin SQL ni reglas de negocio.
- `services`: reglas de negocio (stock, IGV, permisos por dueño, estados).
- `repositories`: consultas SQL. Siempre parametrizadas (`$1, $2`), nunca concatenando texto.
- `validators`: reglas de validación del cuerpo de cada módulo (`modulo.validator.js`), que ejecuta `middlewares/validate.middleware.js`.

## Reglas del backend
- Toda ruta, salvo `POST /auth/login`, usa `verificarToken` y `verificarRol(...roles)`.
- Valida siempre en el servidor, aunque el frontend ya valide.
- Ventas, anulaciones, compras y ajustes de stock van en **una transacción** (`BEGIN` / `COMMIT` / `ROLLBACK`). Al descontar stock usa `SELECT ... FOR UPDATE`.
- Los precios y el IGV se calculan en el servidor con los datos de la base, nunca con los que manda el navegador.
- Cada movimiento de stock inserta una fila en `movimientos_inventario`.
- Errores: `next(error)` hacia el manejador central, con `error.status`. Nunca registres contraseñas ni tokens en `console.log`.
- Cada servicio nuevo lleva al menos una prueba en `tests/`.

## Reglas del frontend
- Llamadas a la API solo desde `src/services/*.service.js`, que usan `apiFetch` de `src/lib/fetcher.js`. Nada de `fetch` directo en páginas ni componentes.
- Usa los componentes de `src/components/ui/` (shadcn/ui) y Tailwind. No crees otro sistema de estilos.
- Valida los formularios en el navegador y muestra los errores por campo que devuelve la API (`campos`).
- Oculta en el menú y protege las páginas que el rol no puede usar.
- SSR para listados, dashboard y reportes; componentes de cliente (`"use client"`) para la caja y los formularios.
- Mientras una ruta no exista en el backend, usa datos de prueba en `src/mocks/<modulo>.mock.js` (cada uno el de su módulo) con la misma forma del contrato.
- Páginas internas dentro de `src/app/(panel)/`; el login en `src/app/(publico)/login/`. Los paréntesis no aparecen en la URL.
- Textos de la interfaz en español.

- vendedor: clientes, ventas y cobros; ve productos y stock; reportes solo de sus ventas.

## Git y commits
- La IA **no** hace commits ni push. Propone los cambios; la persona los revisa y los sube.
- El equipo trabaja **directo en `main`**, sin ramas. No propongas crear ramas ni Pull Requests. Nunca `push --force`.
- Commits en español, en primera persona y con prefijo: `feat: agrego el listado de productos con paginación`. Prefijos: `feat:`, `fix:`, `test:`, `docs:`, `refactor:`.
- Un commit por cambio lógico. No mezcles en un commit cosas de módulos distintos.
- **Sin rastros de IA**: nada de líneas `Co-Authored-By` de asistentes, ni "generado con", ni menciones a herramientas de IA en commits, comentarios del código, README o Pull Requests.
- Archivos por nombre (`git add tecnifix-backend/src/services/ventas.service.js`), nunca `git add .` ni `git add -A`.
- Nunca se suben: `.env` (solo `.env.example`), `node_modules/`, `.next/`, `.vercel/`, `coverage/`, documentos de entrega (`.docx`, `.pdf`, `.pptx`), notas personales, archivos locales de IA, logs ni copias de la base de datos.
- Antes de cada commit y de cada push: `git pull --rebase origin main`, pruebas en verde y `git diff --staged` revisado. Al subir, la persona avisa en Discord.

## Cómo verificar
- Backend: `cd tecnifix-backend && npm test` y `npm run dev` (puerto 4000).
- Frontend: `cd tecnifix-frontend && npm run lint && npm run build`, y `npm run dev` (puerto 3000).

Cómo empezar

Primeros pasos, en orden

  1. Acordar este plan y el contrato de la API entre los 6. Desde ahí cada equipo puede avanzar sin esperar al otro.
  2. Rony agrega a los 5 como colaboradores, sube AGENTS.md, el .gitignore y CODEOWNERS, protege main y conecta el repositorio con Discord. Desde ese momento todas las IA trabajan con el mismo contexto y todos ven los avisos.
  3. Base de cada capa, en paralelo. Rony: migración con las 11 tablas, verificarRol, formato de respuestas y Supabase. Oscar: Tailwind, shadcn/ui y el layout de (panel) con menú por rol; cada uno arma sus datos de prueba en mocks/.
  4. Cada uno, su módulo. En backend, rutas con sus pruebas. En frontend, pantallas que primero usan los datos de prueba.
  5. Subir a main y avisar. git pull --rebase, pruebas en verde, push y aviso en #tecnifix-avisos. GitHub Actions corre las pruebas en cada push.
  6. Conectar de verdad. Cuando una ruta está en main y desplegada en Render, su pareja de frontend deja los datos de prueba y usa la API real.
  7. Prueba completa entre los 6: una compra, varias ventas, una anulación y los reportes con cada rol, y luego el ensayo de la presentación.
